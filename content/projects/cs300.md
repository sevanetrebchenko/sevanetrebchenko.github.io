The first OpenGL graphics framework I ever built was for CS300 (Advanced Computer Graphics I) at DigiPen.
This course revolved around a series of projects, each building on the one before it.
Topics included lighting, texture mapping, cube maps, and basic environment mapping.

## Lighting

The renderer is a forward renderer that supports up to 256 lights at a time.
Light data lives in a single uniform block and is updated every frame, driven by a runtime ImGui editor.
Each light stores its type, position, color, direction (used for directional and spot lights), and the inner/outer cone angles (used for spot lights).
Also stored in the uniform block are members for the global ambient color, distance attenuation and falloff coefficients for point and spot lights, and the fog color.

For this project, I implemented three lighting models: Gouraud (computed per vertex and linearly interpolated across each triangle), Phong (computed per fragment), and Blinn-Phong (like Phong, but uses the half vector between the light and view directions instead of the reflected light direction).
The clips below use Blinn-Phong shading.

![Three colored point lights circling the bunny above a checkered floor, each lighting the floor in a soft pool of its color](/projects/cs300/lighting-point.mp4 "point lights: light falls off with distance")
![Two directional lights, coral and blue, turning around the bunny, the floor fading into fog in the distance](/projects/cs300/lighting-directional.mp4 "directional lights: every surface is lit from the same direction, with no falloff; the spheres only mark where each light comes from")

Point lights emit light in every direction, their contribution scaled by attenuation factor based on the distance of the fragment to the light source:
$$
\text{attenuation} = \min\left(\frac{1}{c_1 + c_2 \cdot d + c_3 \cdot d^2},\ 1\right)
$$

`d` is the distance to the light, and `c₁`, `c₂`, and `c₃` are constant, linear, and quadratic terms that control the falloff.
This mimics the inverse-square law of real light sources.
The constant term keeps the attenuation factor finite for fragments that are close to the light, while the linear and quadratic terms allow for artistic control over the shape of the falloff.
HDR is not supported, so the factor is capped at 1 to limit the contribution of each light and avoid the surface from appearing blown out.

Directional lights model light sources that are placed infinitely far away and emit the same illumination from a single, fixed direction at every point.
A common example of this is the sun.
Directional lights do not use attenuation.

Spot lights are point lights restricted to a cone, represented by an inner/outer angle and light direction.
Fragments within the inner cone are fully illuminated, while those outside the outer cone contribute only the global ambient term.
Between the inner and outer cones, the intensity is interpolated by the cosine of the angle to the light direction.
A falloff exponent controls how soft the edge of the cone is.

The scene also linearly interpolates toward a fog color based on the distance a given fragment is from the camera.
This effect can most clearly be seen in the directional light clip, where the fog is used to hide where the floor plane ends.

## Texture mapping

Texture mapping requires a texture coordinate per fragment.
Texture coordinates are typically authored offline in 3D modeling software and exported alongside the geometry of the model.
For this project, however, texture coordinates are instead generated at runtime by projecting the model onto a simple shape and "unwrapping" that shape onto a texture.
Three shapes are implemented: a cube (planar mapping), a cylinder (cylindrical mapping), and a sphere (spherical mapping). 

::carousel
![The bunny covered in a rainbow grid, spinning inside a faint wireframe box; the grid is stretched where the surface turns away from the box's faces](/projects/cs300/texture-planar.mp4 "planar (six-sided): each point takes the texture from the face of the box it's closest to facing")
![The bunny covered in a rainbow grid, spinning inside a faint wireframe cylinder; the grid wraps around it](/projects/cs300/texture-cylindrical.mp4 "cylindrical: the angle around the vertical axis gives u, the height gives v")
![The bunny covered in a rainbow grid, spinning inside a faint wireframe sphere; the grid's rows bunch together toward the top and bottom](/projects/cs300/texture-spherical.mp4 "spherical: the angle around the vertical axis gives u, the angle from the top gives v")
::

Planar mapping uses six textures, one per cube face.
The largest component of the point's direction vector from the center of the model selects the face of a cube to sample from, and the other two components are divided by the largest to compute the `u` and `v` coordinates on that face:
```glsl
// +x / -x
if (abs(x) >= abs(y) && abs(x) >= abs(z)) {
    max_axis = abs(x);
    
    // Flip sign so u runs left to right when viewed from the outside
    if (x > 0.0f) {
        uc = -z;
    }
    else {
        uc = z;
    }
    
    vc = y;
}
// y and z faces follow the same pattern
// ...

// Remap texture coordinates from [-1, 1] -> [0, 1]
float u = (uc / max_axis + 1.0f) * 0.5f;
float v = (vc / max_axis + 1.0f) * 0.5f;
```

Cylindrical mapping uses the angle around the vertical axis as `u` and the height as `v`:
```glsl
float theta = atan(x, z);  // [-π, π]
float u = theta / (2.0f * PI);  // [-0.5, 0.5]
if (u < 0.0f) {
    u += 1.0f;
}

float v = (y + 1.0f) / 2.0f;  // [-1, 1] -> [0, 1]
```

Spherical mapping also uses the angle around the vertical axis as `u`, and the angle down from the top of the sphere as `v`:
```glsl
float theta = atan(x, z);  // [-π, π]
float u = theta / (2.0f * PI);
if (u < 0.0f) {
    u += 1.0f;
}

float phi = acos(y / length(vec3(x, y, z)));  // [0, π]
float v = (PI - phi) / PI;  // [π, 0] -> [0, 1] so that v increases with y
```

OpenGL uses the bottom-left as the origin for texture coordinates.
However, as most image formats store the top row of the image first, this results in textures appearing upside down.
This is why OpenGL code commonly flips images on load.

Each mapping stretches the texture as a surface runs closer to parallel to the projection direction.
Spherical mapping also exhibits large amounts of distortion for texture coordinates near the poles.

Texture coordinates can be computed in two places.
On the CPU, they're computed once per vertex and uploaded as a vertex attribute, which the GPU interpolates across the triangle face.
However, this breaks down whenever the coordinates wrap: a triangle with one vertex at `u` coordinate 0.98 and the next at 0.02 interpolates through the entire [0.02, 0.98] range for fragments in between.
The entire texture is compressed into that one triangle, resulting in an obvious band along the seam.
When done on the GPU, the texture coordinate is derived per fragment from the interpolated position, and gets the exact coordinate it should with no artifacts.
This is the approach used in the clips above.

These projections are common in 3D modeling software: Blender, Maya and 3ds Max all have box, cylinder, and sphere projections for generating UVs as a starting point.
In games, triplanar mapping projects a texture along each of the three axes and blends the result by the surface normal, which allows terrain and rocks without UVs to be textured easily.
Decals, such as bullet holes or graffiti sprays, project a texture directly onto the surface they're applied to.

## Cube maps

Cube maps are implemented using the same planar mapping derivation code above.

![The camera circling the bunny with a sky and sea all around it, the edges of the six skybox faces drawn as thin white lines](/projects/cs300/cubemap.mp4 "the skybox, with the edges between its six faces drawn in white")

Fragments look up the texture to sample from using their direction vector from the center of the cube.
Each cube face is bound as a separate texture and sampled from independently.

## Environment mapping

Environment mapping uses a cube map to texture an object with the world around it.
At the start of each frame, the scene is rendered six times into a framebuffer, once per cube face.
The camera is placed at the center of the object and pointed along the positive and negative directions of each axis, using a square 90° field of view to avoid seams.
The object itself is hidden (otherwise, every face of the cube map would only show the inside of the model).
The result is a dynamic cube map of everything around the object, including objects that move.

![Six square views of a sky over the sea unfolded into a cross; three small colored spheres sit on the horizon](/projects/cs300/environment-map.jpg "the environment map rendered from the bunny's center, unfolded into a cross; the three colored spheres are lights circling the bunny")

### Reflection

For perfect mirror reflections, the environment map is sampled using the reflection of the view direction about the surface normal:
$$
\mathbf{R} = 2(\mathbf{N} \cdot \mathbf{V})\,\mathbf{N} - \mathbf{V}
$$

![A mirror-finish bunny reflecting the sky and sea as the camera circles it, three colored lights circling above it](/projects/cs300/reflection.mp4 "reflection: the lights circling above show up on the bunny's back and head")

Rendering the environment map from the center of the object has a few limitations.
Reflections start at the surface of the object, not at its center, so the environment map renders the scene from a slightly different position than a reflection would.
This becomes more noticeable the closer an object is to the surface; at the right angle, reflections of a light appear on the bunny before the light itself comes into view.
The lights circle above at about twice the bunny's radius to keep this error manageable.

The object also can't reflect itself, since it's hidden while the environment map is being rendered.
As a result, regions where one part of the model faces another reflect whatever is behind the object instead of the surface of the object itself.
The back of the bunny, for example, should show up in the reflection of the backs of the ears (but doesn’t).

### Refraction

When light enters a denser medium, it slows down and changes direction, following Snell's law.
For a ratio of refractive indices `K` (1 / 1.5 for light going from a vacuum into glass), the refracted view direction is computed by:
$$
\mathbf{T} = \left(K(\mathbf{N} \cdot \mathbf{V}) - \sqrt{1 - K^2\left(1 - (\mathbf{N} \cdot \mathbf{V})^2\right)}\right)\mathbf{N} - K\mathbf{V}
$$

Refraction of light exiting the bunny is not accounted for.
This still gives a convincing approximation, even if not a physically exact one.

The refractive index of a material varies slightly based on the incoming light wavelength.
This effect is called dispersion, and is what causes white light to separate out into a spectrum when passing through a prism.
This project does not simulate light using a full spectrum, and instead approximates this effect with chromatic aberration.
Refraction is computed three times (once per RGB channel) using slightly different refractive ratios.
In the clip below this effect is subtle, showing up most prominently along the very edges of the model.

### Fresnel

The reflectivity of a surface also depends on the angle it's viewed from.
At grazing angles, where the view direction runs nearly parallel to the surface, most of the light is reflected.
Schlick's approximation computes the fraction of reflected light given a surface normal and view direction as:
$$
F = F_0 + (1 - F_0)(1 - \mathbf{N} \cdot \mathbf{V})^p, \enspace \text{where} \: F_0 = \left(\frac{1 - K}{1 + K}\right)^2
$$
`p` is the Fresnel power, which controls the size of the effect.
Higher values correspond to a thinner reflective rim along the edges of the model.
`F₀` is how much light is reflected when the surface is viewed head on.
For glass, this value is about 0.04, or 4%.
The final surface color uses `F` to blend between the reflected and refracted colors.

## What I'd do differently

OpenGL has built-in support for cube map textures, sampled directly by direction with filtering that can blend across faces instead of stopping at them.
This is simpler, faster, and would remove the seams along the edges of each texture when two faces meet.
It would also replace the six individual cube face textures with a single combined cube map texture, and remove the code that picks a face before every lookup.

Generating the environment map is expensive, as the scene must be rendered six extra times per frame at the window's full resolution.
An alternative approach could use geometry shaders and layered textures to render to all six faces at once.
A smaller environment map would improve performance without a visible loss in quality, as highly detailed and curved surfaces shrink the reflected image and don't take full advantage of the extra resolution.
