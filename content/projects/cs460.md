*C++ · OpenGL · DigiPen CS460 · solo · October to December 2021*

CS460 (Computer Animation) at DigiPen was a series of projects on my OpenGL sandbox framework that build up one animated character.
It plays back skeletal animation, walks along a path, and reaches for a target with inverse kinematics.

![A fox, two skeletons and a mannequin walking side by side](/projects/cs460/cover.mp4 "four characters, each playing its own walk")

## Skeletal animation

Skeletons, skinned meshes, and animation clips are loaded using [Assimp](https://github.com/assimp/assimp).
Everything else, including skinning on the GPU and keyframe interpolation between poses, was implemented from scratch.

A debug rendering pass draws the bone hierarchy over the mesh, each bone drawn as a cone from its parent's join to its own.

![The mannequin stepping from a T-pose into a walk and then a sprint, its skeleton drawn over the mesh](/projects/cs460/skeleton.mp4 "the skeleton over the mesh: bind pose, walk, sprint")

### VQS transforms

Bone transforms are represented by a `VQS` (vector, quaternion, scale) instead of a 4x4 matrix.
It holds a translation, a rotation as a normalized quaternion, and a uniform scale factor:
```cpp
struct VQS {
    Vector3 translation;
    float scale;
    Quaternion rotation;
};  // sizeof(VQS) == 32
```

The main reason to use a `VQS` over a standard 4x4 matrix is interpolation.
Interpolating matrix elements one by one does not preserve the rotation, so the mesh shears and/or shrinks mid-blend.
This is similar to using a plain `lerp` to interpolate between two quaternions.
With a `VQS`, the interpolation is split by component: translation and scale use linear interpolation, rotation uses spherical interpolation:
```cpp
VQS interpolate(const VQS& from, const VQS& to, float t) {
    Vector3 translation = lerp(from.translation, to.translation, t);
    Quaternion rotation = slerp(from.rotation, to.rotation, t);
    float scale = lerp(from.scale, to.scale, t);

    return VQS { translation, scale, rotation };
}
```
As a result, every intermediate pose has a valid transform.
A `VQS` is also more compact, requiring only 8 floats (instead of 16 for a 4x4 matrix).

Transforming a point is near identical to using a 4x4 matrix:
```cpp
Vector3 operator*(const VQS& transform, const Vector3& point) {
    // S * R * T
    return transform.rotation * (transform.scale * point) + transform.translation;
}
```

The vertex shader does the same multiplication directly on each bone's `VQS`, without converting it to a `mat4` first:
```glsl
struct VQS {
    vec3 translation;
    float scale;
    vec4 rotation;  // Quaternion (xyz, w)
};

vec3 rotate(vec4 q, vec3 v) {
    return (2.0 * q.w * q.w - 1.0) * v + 2.0 * dot(q.xyz, v) * q.xyz + 2.0 * q.w * cross(q.xyz, v);
}

vec3 transform(VQS vqs, vec3 point) {
    return rotate(vqs.rotation, vqs.scale * point) + vqs.translation;
}
```

Bones are stored relative to their parent.
Each frame, the skeleton is walked from the root down, and each bone is combined with its parent's transform.
Combining two VQS transforms gives another VQS.
The child's translation is scaled, rotated, and moved by the parent, and the rotations and scales multiply.

```cpp
VQS operator*(const VQS& parent, const VQS& child) {
    Vector3 translation = parent * child.translation;
    Quaternion rotation = parent.rotation * child.rotation;
    float scale = parent.scale * child.scale;
    
    return VQS { translation, scale, rotation };
}
```

The inverse is just as cheap, with no matrix inverse involved.
For a unit quaternion, the conjugate is the inverse rotation.

```cpp
[[nodiscard]] VQS inverse(const VQS& transform) {
    VQS result { };
    result.rotation = conjugate(transform.rotation);
    result.scale = 1.0f / transform.scale;
    result.translation = result.rotation * (-transform.translation * result.scale);
    return result;
}
```

The scale is a single number on purpose.
A uniform scale stretches every direction the same, so it doesn't matter whether it's applied before or after a rotation.
That's what lets two VQS transforms combine into one.
A scale per axis doesn't have that property.
If a parent stretches along its x axis and its child is rotated, the stretch no longer lines up with the child's axes, and the result is a shear.
A VQS has nowhere to store a shear.

A per-axis scale is still worth adding later, for effects like squash and stretch.
It works as is for any bone whose parents aren't scaled.
For the rest, there are two common ways around the shear.
One is to keep each bone's scale to itself and not pass it down to its children.
The other is to switch to a matrix wherever a scaled parent has rotated children.

## Interpolating rotations
Between two keyframes, a bone's translation is interpolated linearly, but its rotation is a quaternion, and quaternions don't interpolate like vectors.
A unit quaternion is a point on a four-dimensional sphere, and every rotation in between two keys lies on the arc between them.

A plain linear interpolation cuts straight through the inside of that sphere, so the quaternions in between are shorter than unit length.
Rotating a vector with one, using the usual formula that assumes unit length, doesn't just rotate it.
It shrinks and shears it, and a limb animated that way visibly collapses towards the middle of a blend.
Normalizing the result puts it back on the sphere.
My Lerp does exactly that, and it's close to right.
But the points it lands on bunch up towards the middle of the arc, so the rotation speeds up and slows down between keys.
Slerp moves along the arc at a constant rate.

![Three paths between two rotations on a sphere: a straight chord through the inside and two arcs along the surface](/projects/cs460/interpolation.mp4 "between two rotations: plain lerp (purple) cuts through the sphere, normalized lerp (red) and slerp (yellow) follow its surface, and the two arcs are drawn just inside and outside it so both stay visible")

![Four mannequins playing the same sword attack side by side, each interpolating between the same sparse keys a different way](/projects/cs460/keyframes.mp4 "a sword attack with only every 5th key kept, at 0.35x speed: the keys alone, plain lerp (the arm collapses through the swing), normalized lerp and slerp")

The animator can use either one, picked at runtime, along with an incremental version of each.
Incremental Slerp (iSlerp) splits the arc between two keys into a fixed number of equal steps, 20 here.
Evenly spaced quaternions on a slerp arc follow a simple recurrence.
Each one is 2cos(β) times the one before it, minus the one before that, where β is the angle of a single step.
So after one `acos` and one `cos` to set up the key interval, every further step is a scale and a subtraction, with no `sin`, `acos` or division.
The steps land exactly on the arc, at equal angles, so iSlerp keeps Slerp's constant angular speed at close to the cost of a Lerp.
Incremental Lerp does the same with a fixed step along the chord.
The trade-off is resolution.
The rotation advances in those fixed increments rather than continuously.

Clips can be blended as well.
Both clips are sampled at the same point in their cycle, and each bone's pose is mixed by a single weight.
Rotations use Slerp, the shorter way around, and translations use Lerp.
The playback rate is mixed by the same weight, so the steps of a walk and a run stay in sync through the blend.

![The mannequin blending from a walk into a run and back](/projects/cs460/blend.mp4 "a walk blended into a run and back by one weight")

## Path following
The character walks along a path through a set of control points.
The path is an interpolating cubic spline, ported from my [MAT300](/projects/mat300/) code, solved for its coefficients with Gaussian elimination.

Moving along a spline at a steady speed takes more than stepping its parameter.
Equal steps in the parameter cover unequal distances.
The path is reparameterized by arc length instead, with a table of arc length samples searched by binary search, so a distance along the path maps back to a parameter.
On top of that, the speed follows an ease-in/ease-out curve over the length of the walk (accelerate, hold, decelerate).
The character also faces a point a little further along the path, so it turns into the curves ahead of time.

![The mannequin walking a figure-eight path through its control points, facing a point just ahead of it on the path](/projects/cs460/path.mp4 "a figure-eight through the control points (orange), and the character faces the point ahead of it (purple)")

## Inverse kinematics
Given a target, IK solves for the joint rotations that bring the end of a bone chain to it.
Here the chain runs from the right hand to the base of the spine, so a target further away bends the back as well as the arm, and the legs keep walking.

![The mannequin walking in place with its right hand on a ball that pulls out to the side and down, the body leaning after it](/projects/cs460/ik.mp4 "the right hand held on a moving target, with the arm and spine bones solved while the legs play the walk")

I implemented two solvers.
CCD (cyclic coordinate descent) rotates one joint at a time, from the end of the chain inward, to point the end effector at the target.
It's simple, but it's greedy.
The joints nearest the hand do most of the work, so chains tend to curl and kink before the joints further in move at all, and long chains need many passes to converge.
FABRIK (forward and backward reaching IK) works on joint positions instead, alternating a pass from the target back to the root and one from the root back out, keeping each bone's length.
It spreads the motion along the whole chain and converges in a few iterations.
The joint rotations are recovered from the solved positions afterwards.
The character above uses FABRIK.
